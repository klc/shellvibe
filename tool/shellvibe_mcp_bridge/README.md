# shellvibe-mcp

A tiny, dependency-free stdio-to-HTTP bridge. It is what an MCP client (an
AI agent's tool runner) actually launches as a subprocess: it speaks
JSON-RPC over stdin/stdout, and relays every line to the ShellVibe desktop
app's local MCP server over `http://127.0.0.1:<port>/mcp`. The app must be
running for any of this to do anything — see `docs/mcp_plan.md` for the
endpoint file and HTTP server it talks to.

This package has no Flutter dependency by design, so it is not built with
`flutter build`. It is compiled standalone with `dart compile exe`.

## Building

Run from the repo root, once per target platform:

```
dart compile exe tool/shellvibe_mcp_bridge/bin/shellvibe_mcp.dart -o shellvibe-mcp
```

On Windows, name the output `shellvibe-mcp.exe`:

```
dart compile exe tool/shellvibe_mcp_bridge/bin/shellvibe_mcp.dart -o shellvibe-mcp.exe
```

Each platform's binary must be built (or at least compiled from a checkout)
*on* that platform — `dart compile exe` produces a native executable for the
host it runs on, there is no cross-compilation. In CI this means three
separate build jobs, one per desktop target; `.github/workflows/release.yml`
runs this compile inside each of them, before the bundle is archived.

For a local build, `tool/build_bridge.sh` wraps the compile and drops the
binary in the right per-platform directory for you.

## Where the binary goes

The bridge is not a general-purpose CLI tool the user installs by hand — it
is meant to be pointed at by an MCP client config (the exact JSON block is
generated by the app at runtime, since the real path depends on how it was
installed). Where it physically lives differs per platform:

- **macOS:** inside the `.app` bundle, next to the app's own executable:
  `ShellVibe.app/Contents/MacOS/shellvibe-mcp`. It has to be that directory
  and not `Contents/Resources`, because the app resolves the bridge relative
  to `Platform.resolvedExecutable` (see `_detectBridgeCommand` in
  `mcp_access_settings_section.dart`). **This binary must be signed and
  notarized together with the rest of the app bundle.** An
  unsigned or unnotarized binary gets silently blocked by Gatekeeper — the
  user sees no error dialog, no crash log, nothing. From their point of view
  the MCP tool just "doesn't work," and there is no way to distinguish that
  from a configuration mistake. If this step is skipped or misses this
  binary specifically (e.g. it's added to the bundle in a build step that
  runs after codesigning), the whole feature dies silently on macOS while
  working fine everywhere else.
- **Windows:** placed in the install directory next to the app; the exact
  path depends on install type (per-user vs. machine-wide, MSIX vs. plain
  installer).
- **Linux:** depends on the packaging format. Inside an AppImage the binary
  is not reachable from outside the image by an external process, so there
  the bridge ships as a separate binary installed to `~/.local/bin` instead
  of being bundled with the app image.

The app detects its own actual install location at startup and writes the
real, resolved path into the MCP client config it hands the user — never a
hardcoded guess. Don't treat any path above as more than a per-OS example.
